## 🧠 二、贾维斯怎么"思考"：两阶段调用链

这是整个项目**最核心的设计**，理解了它你就理解了 70% 的代码。

### 为什么是"两阶段"？

如果只有一次 LLM 调用：
> 用户：今天北京天气怎么样？
> LLM：（瞎猜）北京今天晴天，25 度。 ← 错了！LLM 没有实时数据

所以我们拆成两步：

#### 🪜 阶段 A：工具规划（让 LLM 选工具 + 解析参数）

给 LLM 喂一个**超长**的 system prompt（`ToolRegistry.format_for_llm()` 生成），里面写着：
- 你现在是工具选择器
- 你有 9 个工具，每个工具的名字、说明、参数、例子
- 能解决就**只输出 JSON**：`{"tool": "weather", "params": {"city": "北京"}}`
- 解决不了就输出 `{"tool": "", "params": {}}`

然后我们解析 JSON，执行工具，拿到**真实数据**（比如 wttr.in 返回的真实天气）。

#### 🪜 阶段 B：自然语言总结（把真实数据翻译成人话）

把工具结果拼到 system prompt 的末尾，再**第二次调用 LLM**：

> 【工具执行结果】（工具：weather，状态：成功，耗时 230ms）
> 城市：北京
> 天气：晴转多云
> 温度：22°C（体感 21°C）
> 今日区间：18°C ~ 25°C
> 【指令】：请把【工具执行结果】用简洁、自然的中文转述给主人。

这一次 LLM 不会胡编了，因为它有了**确定的事实来源**。

### 这个设计的 3 个好处：

1. **通用**：不依赖 OpenAI 的 Function Calling，任何能做中文的模型都能用（国产模型 100% 兼容）
2. **可观测**：每一次工具调用都写入 `ToolLog` 表，前端能看到完整审计链
3. **可调试**：在「工具矩阵」页可以跳过 A 阶段直接手动执行，定位是 LLM 规划错了，还是工具本身坏了

## 💽 三、记忆系统：为什么要"双数据库"？

贾维斯的记忆分两层：

### 层 1：SQLite `memory_entries` 表（"书架"）

存所有记忆的**原始内容**，字段包括：
- `category`：4 类（user_profile / important / anniversary / conversation）
- `title` + `content`：标题和正文
- `tags`：标签
- `weight`：权重（重要的事权重高，检索时更靠前）
- `pinned`：是否置顶（比如用户说"这个非常重要"）

**适合精确查询**，比如 "列出所有纪念日"。

### 层 2：ChromaDB 向量库（"语义索引"）

把每条记忆的 `title + content` 变成一条向量（一串 384 或 768 个数字），
当用户说"我上次跟我女朋友去哪里旅游了"，这句话也会被转成向量，
去和所有记忆做**余弦相似度匹配**，就可以找到语义最相关的内容。

**适合模糊查询 / 语义检索**，比如"我之前说过我对什么过敏来着？"。

### 为什么不只用一个？

| | SQLite | ChromaDB |
|---|---|---|
| 存结构化数据 | ✅ 完美 | ❌ 不擅长 |
| 按日期 / 分类过滤 | ✅ | ❌ |
| 模糊语义搜索 | ❌（只能 LIKE '%关键词%'） | ✅ 强项 |
| 速度 | 快 | 第一次加载索引略慢 |
| 备份 | 一个 .db 文件搞定 | 一个文件夹 |

两个一起用 = 既有 SQL 的强大查询，又有向量的语义智能。

### 记忆抽取是怎么工作的？

每次用户和贾维斯聊完一次，**额外调用第三次 LLM**：
- system prompt：你是记忆抽取器，从刚才这段对话里抽值得长期记住的事实，输出 JSON 数组
- 没东西值得记就返回空数组

然后把 LLM 返回的事实写进 SQLite + ChromaDB。
这就是为什么你跟贾维斯说"我生日是 6 月 1 号"，下次它会自己记得——因为这条已经被抽出来存进记忆库了。

## 🧪 四、人格系统：为什么叫 "Persona" 不叫 "Config"？

因为它不是普通的配置文件，它是**贾维斯的身份卡**。字段分两部分：

### 静态字段（设定型）
- `name`、`nickname_for_user`、`gender`、`age` → 基础身份
- `backstory` → 长 prompt（写得越长，AI 扮演得越稳）
- `speech_style` → 短 prompt 加强语气

### 动态字段（变化型）
- `affection`（好感度 / 信任度）：0~100，每次对话根据你说的话加减
- `mood`（稳定度 / 心情）：0~100，贾维斯不情绪化，所以默认高（70）
- `mood_reason`：一句文字解释当前状态（方便你调 prompt）
- `total_chats`、`last_chat_at`：统计 + 久未联系判断

### 怎么用这些动态值？

在 `build_system_prompt()` 里，我们把信任度和稳定度**翻译成一段自然语言**写进 system prompt：

```
【主人的信任等级】已建立信任 🛡（信任值 67/100）
【系统稳定度】稳定运行 🟢🟢（72/100，状态说明：全部系统运行正常）
```

LLM 读到这段就会**自动调整语气**：
- 信任度 20 → 更客气、更谨慎
- 信任度 90 → 更随意、偶尔开开玩笑
- 稳定度 20 → 说话更简洁、更"自检"的风格

（注：效果因模型能力而异，强模型（GLM-4 / Claude 3 Opus）效果非常明显，弱模型可能忽略。）

## 🛠️ 五、工具系统：为什么加「白名单」「注册表」「执行器」三层？

对应 jarvis_tools.py 里的三个类：

### 5.1 SAFE_SHELL_WHITELIST + ALLOWED_READ_PREFIXES（安全层）

**问题**：如果给贾维斯 `os.system()` 能力，用户让它"把我整个硬盘删了"怎么办？

**解法**：
- Shell 命令：只允许 `date / uptime / df -h` 等 9 条硬编码的安全命令
- 读文件：只允许读项目目录 + 用户家目录（`~`），读不到 `/etc/shadow` 这类
- 写文件：**默认完全不提供**（要写自己手动加，加的时候想清楚风险）

**设计原则**：默认锁死，要加能力必须**显式**加，而且加完要在 `ToolMeta.dangerous=True` 打标。

### 5.2 ToolRegistry（注册表层）

**问题**：如果每个工具都写在 if-elif 链里，超过 10 个就没法维护了。

**解法**：
- 每个工具 = `ToolMeta`（元数据）+ 一个普通 Python 函数
- 统一用 `registry.register(meta, func)` 注册
- 自动生成：工具列表 API、前端卡片、LLM 的 system prompt、开关状态

### 5.3 ToolExecutor（LLM 选工具层）

**问题**：不同用户问同一件事的方式千差万别。
- "北京多少度" → 应该调 weather
- "帮我看下今天北京会不会下雨" → 也是 weather
- "现在几点钟" → get_time
- "还有几天到我生日" → get_date

手写 if-elif 匹配不了所有情况。

**解法**：让 LLM 选 + 解析参数。容错机制：
- 代码块包裹了？去掉 ` ```json `
- JSON 外面多了字？正则 `\{[\s\S]*\}` 只取大括号部分
- 解析失败？返回 None，当没选工具，用普通对话兜底

## ⏰ 六、定时系统：APScheduler vs Cron

为什么用 APScheduler，不用系统 crontab？

1. **代码内定义**：定时任务写在 Python 里，跨平台（Windows/Mac/Linux 一样跑），不用额外配 crontab
2. **异步友好**：和 FastAPI 共用 asyncio event loop，不会阻塞 HTTP 请求
3. **可以在运行时改**（未来可以做一个 UI 开关定时任务）

当前 4 个定时任务：

| 任务 | 触发 | 频率 | 代码位置 |
|---|---|---|---|
| every_hour_check | 早 7:30 早安 / 晚 23:45 睡前 | 每小时（整点），对比时间匹配 | app.py |
| every_day_miss_check | 7 天没说话主动联系 | 每天 20:00 | app.py |
| every_30s_reminder_poll | 倒计时提醒到点触发 | 每 30 秒 | app.py |
| （贾维斯内部） | 记忆抽取 + 向量同步 | 每次对话后即时触发 | brain.py |

## 🎨 七、前端架构：为什么 Vue 3 + Element Plus？

### 为什么不是 React？
- Vue 3 上手更快，你学维护成本低
- Element Plus 现成组件多（Table / Form / Dialog / Progress 都有），省得自己写
- Vite 构建快，`npm run build` 5 秒搞定

### 为什么是「HUD 风格」？
贾维斯在电影里的视觉特征非常明确：
1. 深蓝背景 + 霓虹青蓝（#3fd5ff）
2. 扫描线（scanline）
3. 电弧反应堆（电弧圈光圈）
4. 四角装饰框（corner brackets）
5. 等宽字体显示数据（Menlo / SF Mono）

所以 `style.scss` 里的设计：
- 全局扫描线（`body::before` 的 repeating-linear-gradient）
- 颜色变量 6 条（改这 6 条 = 换主题）
- `.jarvis-card` 通用卡片（带淡斜纹背景 + 角标）
- `.arc-reactor` 电弧反应堆 CSS 动画

### 前端为什么"前后端分离"？

好处：
1. 后端纯 API（FastAPI），未来你想加 Telegram / 飞书 / 微信机器人，**只写一个新 client 就行，后端 0 改动**
2. 前端纯静态（Vite build 出来 dist/），可以放 CDN / 对象存储，不占后端服务器性能
3. 调试方便：前端有 bug 只改前端重新 `npm run build`，不用重启后端（Python 进程）

## 🚧 八、扩展方向（架构上已经预留了口子）

| 你想做的功能 | 架构位置 | 改动量 |
|---|---|---|
| 加新工具 | `jarvis_tools.py` 加函数 + 注册 | 15~30 行 |
| 加新数据表（Todo / Note 等） | `db.py` 加表 + `app.py` 加 API | ~50 行 |
| 接新模型供应商 | `llm.py` SUPPORTED_PROVIDERS 加一条 | 0~10 行 |
| 改人格 / 说话风格 | 网页「人格配置」页面 | 0 行代码 |
| 改情绪规则 | `brain.py` TRUST_AFFECT_RULES 改正则 | 几行 |
| 加新定时任务 | `app.py` lifespan 加 `sched.add_job(...)` | ~15 行 |
| 加新前端页面 | 复制一个 Vue + main.js 加路由 | ~20 行 |
| 换向量数据库 | 改 `memory.py`，把 ChromaDB 调用换成 Qdrant / Milvus | 约 100 行（接口保持不变） |
| 换数据库 | 改 `db.py` make_engine 的连接串 | ~5 行（SQLite → PostgreSQL） |
| 多用户 / 登录系统 | `db.py` 加 User 表 + 所有表加 user_id + FastAPI Depends 加 auth | ~200 行（架构侵入较大，但代码本身不难） |

## 🧭 九、技术选型的权衡

| 技术 | 为什么选它 | 代价 / 不足 |
|---|---|---|
| SQLite | 零配置、一个文件随便拷、性能够个人用（10w 行以内无压力） | 不支持高并发写入（但个人项目用不到） |
| ChromaDB | 纯 Python，零配置，内置 embedding 模型（不用额外 API Key） | 数据量 > 10 万条后会变慢，可以换 Qdrant |
| FastAPI | 原生 async、自动生成 Swagger 文档、类型安全 | 学习曲线比 Flask 略陡 |
| Vue 3 + Element Plus | 中文文档好、组件全、维护成本低 | 包体积 ~1MB（首屏加载 1~2 秒，可接受） |
| APScheduler | Python 内解决，跨平台 | 如果后端重启，错过的 cron 点不会补跑（对个人项目无所谓） |
| 不使用 LangChain / LlamaIndex | 这两个框架太重，1000 行能解决的事不用带 50MB 依赖 | 一些高级功能（Agent Tool Loop）需要自己手写 |
